## Module contracts
- workflow.mjs exports WORKFLOW as an array of {name,role,color}, roles backlog|ready|active|review|done; legacyRole(value) returns a canonical role (planning=>ready, parked/unknown=>backlog); ensureProjectWorkflow(store,projectId) returns the canonical ordered stages; migrateWorkflow(store) applies all projects transactionally. Existing matching canonical-role stage IDs survive; write only when changed. Never emit events or queue unsolicited GitHub writes from this migration. Tickets that genuinely need a remote status change remain discoverable through normal sync comparison without dropping pending intent.
- AgentStatusMonitor constructor({agents,collectors?,clock?,ttlMs?}); agents is an array of agent IDs. snapshot() returns {agents:AgentCapacity[],refreshing:boolean}; refresh() is a coalesced Promise; close() terminates owned processes/resources. No automatic collection on constructor. GET status triggers stale refresh in HTTP; POST refresh requests refresh; monitor retains stale observations on failure. Default freshness TTL five minutes; UI can poll cached status every 30 seconds.
- AgentCapacity = {agentId,status:'available'|'limited'|'auth_required'|'unavailable'|'unknown',windows:[{id,label,usedPercent:number|null,remainingPercent:number|null,resetsAt:string|null,windowMinutes:number|null}],source:string,observedAt:string|null,stale:boolean,message:string,ordinaryUsageAllowed?:boolean|null}. Provider-specific permission flags may appear on individual windows. Never infer account-wide permission from an unrelated model bucket.
- GET /api/agents/status returns snapshot; POST /api/agents/status/refresh returns 202 snapshot after initiating coalesced refresh. Both admin-only. Test server injects collectors or status monitor; no native provider calls in CI.
- POST /api/tickets/:id/start is explicit Start, using Runner.start(id,{automatic:false}). Automatic event starts pass automatic:true. Execution purpose is 'implementation' or 'resolve_blockers'. Explicit Start chooses resolution if blocked, has unfinished dependencies, or is Backlog. Ordinary Service.claim and MCP claims retain readiness checks. A trusted internal claim option grants resolution only to Runner, never request JSON.
- Scoped /api/tickets/:id/resolution-context GET requires query executionId/sessionId. PATCH /api/tickets/:id/agent-update requires executionId,sessionId,version,reason,changes. POST /api/tickets/:id/subtasks requires executionId,sessionId,reason,title,description?,brief?. Agent identity comes from auth; admin may supply agentId for local integrations. An active matching assigned claim is required. Update allowlist: title,description,brief,stageId (except Done),blockedReason,parentId,dependsOn. Subtask inherits project/owner, starts Ready. Reason is a non-empty bounded audit entry. Existing full validation applies.
- MCP adds desk_get_resolution_context, desk_update_task, desk_create_subtask using those routes and configured agent identity. Existing tools remain compatible.

## Risks and verification
Retired-stage migration and legacy reimport are the highest data risks; preserve identity and intent atomically. Provider status must be bounded, passive, redacted and isolated from execution readiness. Resolver privilege must be scoped to an active owned claim; starting a resolver does not authorize arbitrary related-ticket writes. Test these boundaries before broad UI checks. Do not start real user tickets as a smoke test.

## Explicit contract revision 1

Integration clarified two visible details: managed Start moves the claimed ticket to In progress before spawning (failures remain visible as failed executions, never Done), while keeping blockers and dependency edges. Capacity refresh accepts internal refresh({force:false}) by default with attempt cooldown; the explicit POST passes force:true for an intentional retry. Forced overlapping requests still coalesce. No request body can choose provider execution arguments.
