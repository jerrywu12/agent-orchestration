# Implementation Plan
Node 22+/SQLite service and React/TypeScript UI; no new dependencies. Reuse synchronous Store transactions and Runner. Existing constitution is an unfilled template; AGENTS.md governs preservation, testing and independent review.

## Locked interface
Extend brief with optional string fields `specification`, `allowedPaths`, `conflictKeys`, alongside `acceptanceCriteria`, `scope`, `verification`; each max 10000 characters. All six required for Ready. Paths are newline-separated repository-relative files/directories or terminal `/**`; conservatively handle wildcards and reject traversal/absolute paths. Keys are newline-separated normalized identifiers or `none`.
GET `/api/tickets/:id/readiness` → `{ready:boolean,missing:string[],holds:string[],conflicts:Array<{ticketId:string,key:string,title:string,reasons:string[]}>}`.
POST `/api/tickets/:id/transition` accepts `{version,stageId,ownerId,confirmed:true}` → `{ticket,outcome:'started'|'queued'|'failed',reason?:string}`. Existing admin authorization applies. Validate target role planning/ready, current version, owner, exact active claim and readiness; atomically save stage/owner and launch intent. Pre-admission rejection rolls back; post-admission launch failure remains visible. Only confirmed pending launches are queued. Recheck at dispatch. Plain PATCH into Planning/Ready requires confirmation; internal trusted service transition can perform admission. New Ready records require readiness but cannot implicitly start. New scoped children start Planning.
UI saves content before readiness preview; cancel never changes stage/owner. Expose preparation fields, preview, selected owner and explicit confirm/start; present queue/failure outcome. List and details share transition UI. Creation captures Backlog, then opens transition if requested Planning/Ready.
Planning interface clarification (2026-09-13): `create_subtask` also accepts optional `dependsOn:string[]` for existing same-project tickets. This lets the parent planner encode sibling execution order while creating children, without claiming or modifying a sibling. Existing dependency validation and cycle checks apply; project and owner still inherit from the parent.
Planning executions stay Planning with purpose planning and planning-only packet; finish checkpoints prepared work. Parent containers with children cannot launch implementation. Implementation claim revalidates preparation/conflicts, preserving same-session retries. Snapshot execution scope so edits cannot shrink it. Compare canonical repo identities across projects; unknown competing scope blocks clearance. Imported/synced records preserve history but never grant launch approval.
