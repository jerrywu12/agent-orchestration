# Shared development efficiency

Applies to all current and future projects on this machine. Project instructions, approval boundaries, tests and release gates still apply.

- One lead agent owns the task and integration. Delegate only independent bounded questions or worktrees; avoid automatic all-agent fan-out. Give objective, exact root/SHA, allowed paths, relevant evidence, acceptance check and a short return format. Do not copy the whole conversation. A worker returns result, paths, checks and unresolved risks; the lead owns verification.
- Claude: planning and diagnosis. Codex: implementation, tests and git work. Gemini/Antigravity: targeted review or independent work when requested. Ollama: bounded local analysis with an already installed model. ArkCLI: bounded remote advice using the existing profile and model. Never silently switch models/providers or send credentials/customer data.
- For a new project, run `agent-serena project create /absolute/root --language <language>` once, repeating `--language` for every language requiring symbol lookup (Python + TypeScript for mixed web/backend repos). Preserve existing Serena project settings. Noninteractive auto-detection selects only one language. Before reading large source files, activate the exact absolute worktree using Serena and inspect a symbol outline or references. Request function bodies only when needed. Its shared configuration exposes navigation only. Use ripgrep for literals/configuration and native tools for edits. Do not add another graph/index tool for the same question or perform full-repo onboarding routinely.
- Use `agent-run -- <project-owned check>` for noisy commands. It executes once, retains a private full log, returns the actual status and bounds displayed output. Read the full log whenever a failure needs detail. Use `rtk git status`, `rtk git log`, or `rtk grep` for routine discovery. Use raw Git diffs for final review. Never wrap permission-sensitive commands to evade the host's approval boundaries.
- Load the relevant task-packet section and one existing pattern; keep source of truth in files. Consult advisers with compact evidence only when useful or project-required. Check focused tests while iterating and run required full gates before shipping. Stop speculative retry loops and revise the causal model after two failed fixes.
- `agent-advice --provider ollama --model <installed-model> --prompt-file <brief>` and `agent-advice --provider arkcli --prompt-file <brief>` provide advice, not repository tools. Defaults cap the brief at 16 KiB and generation at 512 tokens. Provider usage is separate from command-output byte measurements. Keep subscription usage, cached input and API spend distinct; optimize cost per accepted task, including retries.

## Parallel development and ordered handoffs

Use these defaults for current and future work, within the user's authorized scope.

- Name one lead responsible for the complete outcome, integration order, review, release and installed verification. Each worker owns a bounded result; delegation does not transfer the lead's accountability.
- Before dispatch, check current tickets, exact claims and saved work. Reuse canonical tasks and checkpoints. Record objectives, base SHA/root, owned paths, shared contracts/resources, acceptance checks, forbidden side effects and return format. Do not dispatch duplicate work or assume a parent claim grants child scope.
- Parallelize only when behavior, interfaces, acceptance checks and runtime resources are independent. Different files alone are insufficient. Give each implementation its own branch/worktree, ports and test data; worktrees share Git metadata and do not isolate databases, caches or provider locks. Never apply concurrent results to one checkout.
- For shared APIs/types, schemas, migrations, lockfiles, generated artifacts, auth, global configuration or release state, establish the contract first and serialize mutations through one writer. Consumers may prepare against a reviewed contract only within their own admitted scope. Record an explicit reviewed handoff before changing ownership; integrate approved results one at a time and run the combined smoke check.
- Distinguish four waits: a hard dependency requires verified prerequisite completion; a reviewed milestone permits only the work its stable contract supports; a scope conflict waits for an explicit ownership handoff; a resource wait queues only the operation using that resource. Do not turn every wait into a whole-ticket Done dependency, invent cycles or weaken existing acceptance criteria.
- Keep changes small and branches short-lived. Start with the smallest useful number of workers, normally no more than four concurrent implementation tasks; project-specific higher limits need clear independence and available capacity. When review, integration or tests are the bottleneck, finish that queue before adding builders.
- Queue heavy tests, provider access and shared deployment separately. Continue independent focused work while a resource is occupied. Record the current holder and observable release condition; never stop another agent's process or infer release from an old heartbeat. Verify repository support before relying on a hosted merge queue; otherwise use the existing explicit integration order.

## Actionable communication and durable checkpoints

- Every diagnosis or blocker update must include the corrective action being taken and the next verification or scheduled check. If a product decision or new authority is genuinely required, ask one concrete question explaining what it unlocks. Do not end with a passive FYI, offer-to-continue or request for the user to announce prerequisite completion.
- Continue already authorized work without repeat approval. A scope conflict needs a proper handoff; a real permission boundary needs the specific missing authorization. Do not turn routine reversible implementation choices into extra approval gates.
- Save a compact checkpoint before stopping: canonical task and native session/execution, exact root/base/head, owned scope, changed paths, actual check receipts, unresolved findings, blocker owner, next action and precise resume condition. Distinguish planned, running, passed, reviewed, merged and installed evidence. Preserve unrelated work and failed receipts.
- Keep adviser requests bounded and evidence-based. On timeout or unavailability, record the limitation, use a bounded retry or an allowed fallback, and continue independent local work. Do not change credentials, providers or services merely to obtain advice; required project review gates remain in force.

## Automatic follow-through for sequential work

- When authorized work must wait for another task, gate or shared resource, schedule its next check before ending the turn. Prefer supported completion events while the session is active and a persistent thread heartbeat for later resumption. Reuse a matching monitor; use a 15-minute fallback interval unless the project or user specifies another cadence. Use the supported automation tool, not an improvised daemon or cron job.
- Save the monitor identity with the checkpoint. Its prompt must name the canonical tasks, preserved branch/head, exact readiness evidence, next authorized action and completion condition. Keep unchanged/non-actionable checks quiet; notify on meaningful progress, completion, failure or a specific required user action. Verify the schedule is saved and active; tool availability or intended scheduling is not proof.
- At wakeup, inspect fresh prerequisite, claim, scope and resource state. Resume automatically when the recorded condition is proven: continue the still-valid owned execution, or obtain a fresh exact-session claim after normal readiness admission if the previous execution was released. Respect current holds and newer user steering. Never reuse a released execution, steal a live/stale claim, force admission or clear a hold because time elapsed. If separately authorized blocker resolution is needed, ask that precise question while continuing independent work.
- Scheduling authorizes neither new scope nor messages to other chats/people. Respect explicit pauses/cancellations and existing messaging permissions; do not reactivate unrelated paused work. If persistent automation is unavailable, save the checkpoint and state that automatic continuation is unavailable rather than promise it.
- After the original acceptance criteria, required gates, independent exact-head review, merge and relevant installed journey are verified, pause the matching monitor and record delivery. A scheduler run, test pass or merge alone does not prove the user's issue changed.

These defaults are informed by [effective agent workflows](https://www.anthropic.com/engineering/building-effective-agents), [durable agent sessions](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), [Git worktree isolation](https://git-scm.com/docs/git-worktree), and DORA's [small batches](https://dora.dev/capabilities/working-in-small-batches/) and [work-in-process limits](https://dora.dev/capabilities/wip-limits/). They guide execution; project contracts and existing safety/release gates still govern admission and delivery.
